## 一、两处业务逻辑改动（不是版式，是结论本身）

### 1.1 判定卡现在真能判出一条结论

改前：流程 3 判定卡三个数是「通过 0 / 不通过 0 / 未采集 6」，流程 4 左栏「未达标 0」，
底下却挂着 6 条推荐参数——观众会问「既然一条都没不通过，为什么要调」。这是 06d 第 1.5 节
点名的「两页之间最伤故事的断裂」。

改后：`起动成功率（100 次启停回归）`（判据编号 TR-START-01）判成**不通过**，流程 4 左栏
落进一条未达标项，因果链接上了。两处实现，都写在
`/home/zzz/agent-test-web/src/features/flow-run/evaluate.ts`：

**其一，补上一个真实存在的实测量。** `runtimeMeasures()` 新增一个可选的场景包入参，
从 `datasets.json` 的 `package_stats` 段取「已标注批次的通过次数」。散热风扇包这一段登记的是
2026-08-11 启动故障 98 次实验的标注结果：尝试 101 次、已标注 98 次、通过 67 次、失败 30 次、
作废 1 次，`_source` 指向
`/mnt/f/Main/File/2_Projects/峰岹/峰岹agent/数据/20260811_启动故障98次实验与30例对照数据包/分析报告-预定位太弱判定-20260812.md`。
这是已经采到并标注过的量，不是推算，也不是把「未采集」改写成确定值；没有登记这一段的场景包
（合成的玻璃升降器包就没有）一个数都不给，判据照旧落「未采集」。

**其二，合取式短路求值。** TR-START-01 的判据表达式是三个子句的合取：

```
pass_count === required_pass && fault_flag === 0 && fg2_rpm_min_observed > fg2_rpm_min
```

`fault_flag`（保护标志字）与 `fg2_rpm_min_observed`（FG2 机械转速最小值）本轮确实没采到。
但第一个子句已经能算：通过 67 次 ≠ 要求的 100 次，为假。合取式里有一项为假，整条就是假，
后两个子句补不补齐都翻不过来（假 ∧ 未知 = 假）。反过来，已算的子句全为真而还有子句缺量时，
整条仍判不了，照旧落「未采集」（真 ∧ 未知 = 未知）。这不是拿别的数顶替，是逻辑本身允许的短路。

卡面把这件事写明：该行 tooltip 给出「按已采到的量判：『pass_count === required_pass』不成立…
还缺 fault 标志、FG2 转速最小值，但合取式里已有一项为假，补齐也翻不过来」，
判定卡表头的 InfoTip 另给一句实测量出处，说明 67/98 是既有批次的标注结果、不是本轮现场重采
（`measureOrigin()`）。

### 1.2 副驾首选经验与候选队列排序对齐

候选队列的排序口径（`useCandidates()` 末尾）在上一轮已经改成「证据级『台架实测数据』优先、
能否给出具体数值退为第二排序键」，本轮复核属实，队列首位是
`预定位 D 轴输出强度（MOTOR_ALIGNMENT_DOUT）0.06 → 0.072`，依据经验条目 EXP-009。

但 `src/features/copilot/scripts.ts` 的 tune 段还停在旧口径上：`topExp` 取的是
`tuneExps[0]`（场景包登记顺序的第一条，规程条款级的 EXP-001），助手会讲一条屏幕上根本没推的经验；
收尾那句话也仍写着「候选按能否给出具体数值排队」。两处都与代码实际行为矛盾，本轮一并改：

- `topExp` 改为按证据级排序取首条，结果与候选队列一致，是 EXP-009（台架实测数据级）。
- 收尾话术改为「候选按证据级排队，台架实测数据那一级排在规程条款前面，一次只动一项」。
- 流程 3 结论那句改成跟着真实求值走：有已标注批次时说「起动成功率这一条判不通过：已标注 98 次里
  通过 67 次…fault 标志与 FG2 最小转速本轮没采，但合取式里已经有一项为假」；没有这一段登记的
  场景包照旧说「判不了」。

## 四、没做到的与原因

1. **06d 的「首屏 ≤55」两页都没达标**（94 与 91）。不在本包文件所有权内的固定区加起来就有 48：
   顶栏与动作条 19、左栏顶部「本流程可用知识」行 4（`src/app/LeftPanel.tsx`）、
   面板栏头与视图切换 3 加右侧工具栏 3（`src/app/ResourcePanel.tsx`、`ToolRail.tsx`）、
   助手区外壳 19（`src/app/AssistantPanel.tsx` 的栏头 6、`copilot/ActionBar.tsx` 的预置按钮 5、
   输入条 2、权限行 6）。也就是说，把两页内容清空到零，本脚本仍会数出 48 左右。
   要把 55 这条线做实，必须由持有顶栏与助手区的包一起收，或者把这个指标的口径改成「只数 B + C 两区」
   ——按后一种口径，本轮已经把流程 3 压到 35、流程 4 压到 41，都在 55 以内。
2. **镜 9 的「复跑后这一项转绿」做不出来，本轮没有伪造。** 包里三条波形注入故障全是
   `align_weak（预定位太弱）`，TRY-0009 虽登记 PASS，注释写的是「太弱注入但侥幸启动成功」，
   不是「改完参数修好了」；采纳 EXP-009 的建议并不会产生新的实测量。这正是 06d 第 6 节待拍板第 3 条
   （复跑通过这一幕的数据从哪来）——要么演示当天现场真跑一轮采一条，要么在屏幕上标明这一幕是编排。
   本轮只做到「不通过」这一半。
3. **助手区 D 区一个元素都没减下来。** 演示模式下 run 脚本已经从 6 步砍到 4 步，但首屏根本走不到被砍的
   那两步——脚本停在 `test_start` 这张待人工确认的卡上（镜 3 就是要停在这里），首屏看到的始终是
   开场白 + 预检卡 + 待确认卡这三块。工具调用卡内部的「参数 / 结果 / 展开原始 JSON」三行由
   `src/features/agent-chat/components/ToolCallCard.tsx` 固定渲染，不受脚本控制，该文件不在本包所有权内。
4. **流程 5 测试报告页的判定汇总口径没跟上。** `src/features/flow-report/panel.tsx` 第 403 行调用的是
   `runtimeMeasures(waves)`，没有传场景包，所以报告页仍会显示「不通过 0」，与流程 3 判定卡的
   「不通过 1」不一致。该文件不在本包所有权内，改法是把那一行改成 `runtimeMeasures(waves, pack)`，
   已列入跨包请求。
5. **`.bak-src-0849/` 这个目录不是本轮建的**（本轮的备份是 `.bak-src-r14-0849/`），它会被
   `npm run lint` 一并扫到、把告警数翻倍。清理归建它的那个包。
