## ⚠️⚠️ 重大教训：后端与设备桥 mcp 依赖「starlette 死结」，绝不能共用一个 conda 环境

### 死结根源（依赖链硬冲突）
- **后端 fastapi 0.109** 硬要求 `starlette >=0.35.0, <0.36.0`（旧版，客户锁定）。

  本机 ra 是 3.11.16 + fastapi 0.109（旧 fastapi）。**设备桥和后端本来就是两个环境。**

- `conda install mcp` 会把 starlette 升到 1.3.1、连带删掉 pip 装的 pydantic 2.5.0 核心文件（`__init__.py`）、

### 关键事实（读源码确认，纠正了此前的误判）
1. **FTGeneralUtils.dll 12 个导出函数，没有「写单参数/寄存器」函数**（只有 ReadMemValue 读内存，无写寄存器）→
   `write_param` 无法单命令下发，只能走 GeneralMakeFiles→DownloadCode 编译烧录链（需固件工程+hex，现场层硬阻塞）。
2. **dll-bridge 的 IPC 协议**：请求 `{"id","timestamp","payload":{"type":...}}`（camelCase），type 取值
   initDll/dllPath、setCallBackFun、freeRun/mainAddr、breakRun、reset/address、downloadCode/chipName+projectPath、shutdown；
   响应 type=ready/dllLoaded/success(requestId+data)/error/callbackEvent。FreeRun=SetBreakPoint→EnterDebugMode→FreeRun（worker 阻塞，
   BreakRun 主线程中断），**固件已烧时直接 free-run 即可启动，不强制每次烧固件**。
3. **判定是假的根因**：`beginRun` 纯计时器；`evaluateAll` 的 control-parameters 变量读 `pack.controls.parameters` 原值；
   后端 `evaluate.py` 读场景包 control-parameters.json 原值。三处都读原值 → 改了采纳参数结论不变。

## ✅ 助手「跨轮记忆 + 轮内重复检索短路」优化（2026-09-29，代码已改 + 验证 16/16）

用户诉求：助手每次都要重复搜多次一样的东西，换页面也一样，模型"记不住"；要按本项目特点加记忆机制 + 优化回答。

### 三根因（已逐行核实，无误判）
1. **跨轮零记忆**：`agent_stream.py:279` 硬编码 `history=None`，前端 dshAdapter 明明传了 `session_id` 却从不读 → 每轮从零检索。
2. **轮内重复**：`agent_chat_service.py` 循环里无"同名同参已执行就跳过"判断；`agent_tools.py` 的 `KNOWLEDGE_SEARCH` 里一段英文 `Self-check` 把"再调一次"写成可执行分支，datasets 七库被强调"ALWAYS pass ALL" → 同 query + 同七库连发三次（8s×3）。
3. **上限太高**：`AGENT_CHAT_MAX_ITERATIONS=20`，最后一轮才禁工具 → 最多空转 19 次。

### 关键事实（永久记住）
- 项目里**早有** `Chat` 消息树模型（`app/models/chat.py`，open-webui 语义，`chats` 表），但助手 `/api/agent/stream` 链路**完全没用它**。为不污染客户 open-webui 树语义，**新建独立轻量表** `agent_chat_memory`（键 `(user_id, session_id)`）。
- **建表注册点** = `app/db/session.py` 的 `init_db()` 第 65-91 行逐个显式 import（不是 `models/__init__.py`）。新 model 必须在那里加一行 import 才会被 `create_all` 建表。
- **audit_auth_coverage 的 OWN_MODULES 只扫路由文件**，新增 model 不影响。
- session 风格：记忆读写 helper 走 `agent_chat_service.py` 的手动 `with Session(engine) as s` 风格（async generator 无法走 Depends 注入）。
- session_id 前端已有约定：流程页 `shell-<sceneId>-<flow>`、知识库页 `shell-<scene>-knowledge`，沿用不另造。

### ⚠️⚠️ SQLAlchemy JSON 列变更检测坑（永久记住）
- **直接读回 list 原地 append 再赋值 `row.messages = msgs` 不落库**（SQLAlchemy 认为引用相同、无变更）。实测：同 session 追加 + 换 session 追加都不写库，读回永远是首次内容。
