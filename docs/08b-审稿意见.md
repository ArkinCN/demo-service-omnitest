审稿对象：`docs/20260919-通用Agent测试系统v2.0/08b-场景包契约` 全部产物，即 `README-场景包契约-v1.0.md`、`schema/` 下 12 份 JSON Schema、`validate.py`、`examples/minimal-scene/` 十一份 JSON。

审稿日期：2026-09-20。审稿方式：实跑校验器、两轮变异测试、按 README 第 10 节实建第三个场景包并接进前端浏览器验证。

## 一 · 总评

**结论：需修订后放行。** 契约的骨架是对的，事实是硬的，但有一条阻断项：照 README 给的骨架包起手建第三个包，`validate.py` 全绿，接进前端六个页面里有三个直接白屏。

分三句说清楚。

**事实层可信。** README 里 20 项条数声明（两个实物包各十份文件的条目数、副驾按钮 29 枚）、28 个图标名、自检脚本 392 行、schema 12 份、包二那条唯一失败项的定位与修法，逐条复核全部属实，没有一处灌水。契约确实是从两个实物包归纳出来的，不是纸上设计。

**结构校验够用，语义校验几乎为零。** 66 项变异里拦住 45 项。拆开看：改坏文件结构的 43 项拦住 39 项（90.7%），改坏跨文件引用与业务自洽的 23 项只拦住 6 项（26.1%）。README 第 11 节认领了其中一部分缺口，但认领得不全，且把兜底寄托在一个只有一半实物包拥有的脚本上。

**人读版与机读版不等价。** 12 份 schema 把 11 个字段设成必填，README 一个字没提，其中 `demo_profile` 还是前端演示模式的驱动数据。按 README 从零手写一份新包必然挂；只有照抄骨架包才活得下来。契约的说明书因此不能独立使用。

计数：阻断 1 条，主要 9 条，次要 8 条。

## 二 · 阻断项

### 阻-1 骨架包缺报告模板文件名，schema 也不要求，导致照它建的包前端三页白屏

**位置**

- `examples/minimal-scene/report-template.json`：顶层只有 `schema`、`scene_id`、`generated_by`、`generated_at`、`belongs_to_flow`、`group_tiers`、`spec_sections` 七个键，既无 `template_file` 也无 `template_source`。
- `schema/report-template.schema.json` 顶层 `required`：`["belongs_to_flow","generated_at","generated_by","group_tiers","scene_id","schema","spec_sections"]`，两个模板定位字段都不在内，且两者之间没有 `oneOf` 约束。
- 前端崩点一：`[源] flow-init/panel.tsx:444`，`value: fileName(pack.report.template_file).slice(0, 22)`，其中 `fileName` 在 `[源] scene/pack.ts:624` 是 `(p: string) => p.split('/').pop() ?? p`，对 `undefined` 直接抛 `TypeError`。
- 前端崩点二：`[源] flow-report/panel.tsx:110`，`templateTitle(raw)` 第一句就是 `raw.startsWith('/')`，同样对 `undefined` 抛错。
- 归一化不补这个字段：`[源] scene/pack.ts:510`，`if (!pack.report.template_file && src) pack.report.template_file = ...`，`src` 取自 `template_source`；两者都没有时该字段保持 `undefined`。

**实测证据**

把骨架包复制成 `hvac.indoor-unit.cross-flow-fan`、按 README 第 10 节第一步全局替换场景标识后，`validate.py` 十一份文件加跨文件检查全 PASS、退出码 0。把同一份包放进前端 `public/scenes/` 并在 `index.json` 挂上三级节点，用 Playwright 逐页打开（沙箱副本，未改动 `[源] zzz/agent-test-web` 本体）：

| 页面 | 结果 |
|---|---|
| `/init` 初始化配置 | 白屏，`TypeError: Cannot read properties of undefined (reading 'split')` at `fileName` |
| `/req` 测试需求确认 | 白屏，同一个报错 |
| `/run` 启动测试 | 正常渲染 |
| `/tune` 调优运行 | 正常渲染 |
| `/report` 测试报告 | 白屏，`TypeError: Cannot read properties of undefined (reading 'startsWith')` at `templateTitle` |
| `/knowledge` 知识库 | 正常渲染 |

对照组：同一套沙箱下，两个实物包（散热风扇包、玻璃升降器包）六个页面全部正常渲染、无页面错误。所以崩的原因不在沙箱，在骨架包。

给骨架包的 `report-template.json` 补上一行 `"template_file": "..."` 后重跑，六个页面全部正常渲染。一个字段定位准确，无其他连带问题。

**为什么算阻断**

README 第 10 节第一步第 3 条明确要求「把 `examples/minimal-scene/` 十一份 JSON 复制进去，全局替换场景标识，跑一遍 `validate.py` 确认起手就是绿的」。开发照做会得到一个全绿但跑不起来的包，而且崩的是第一个要打开的页面（初始化配置）。契约的承诺是「过了校验就能被前端读进去」（README 第 9.3 节原话），这里直接违约。

**修法**（三选二即可，建议全做）

1. `schema/report-template.schema.json` 顶层加 `"anyOf": [{"required":["template_file"]},{"required":["template_source"]}]`，把「报告模板必须有一个可定位的名字」写进机读契约。
2. `examples/minimal-scene/report-template.json` 补 `template_file`，值写成占位路径并挂 `_placeholder: true`，与骨架包其余字段的占位口径一致。
3. 前端两处收口：`fileName` 改成接受 `string | undefined` 并对空值返回 `'—'`；`templateTitle` 同理。这一条属于前端加固，不属于契约修订，但能把同类问题一次性挡住。

## 三 · 主要问题

### 主-1 校验器的目录名一致检查，在 README 推荐的命令下从不执行

`validate.py:122`：

```python
if re.match(SCENE_ID_RE, dirname) and sid != dirname:
```

只有目录名本身长得像合法场景标识时才比对。逻辑后果是反的：目录名写错成任何不合三段式的形状（少一段、带大写、带下划线），这条检查整条跳过，静默通过。

实测：目录名 `hvac.indoor-unit`（两段）、`scene.json` 的 `id` 为 `hvac.indoor-unit.cross-flow-fan`（三段），跨文件检查报 PASS。而这正是前端按 `/scenes/<sceneId>/` 取文件时会 404、整包加载判失败回落的情形。

更糟的是 README 第 10 节第五步给的命令是：

```bash
python3 .../08b-场景包契约/validate.py .
```

传 `.` 时 `os.path.basename(os.path.normpath("."))` 得到 `"."`，同样不匹配，这条检查在官方流程里永远不跑。

修法：把条件反过来——目录名不匹配 `SCENE_ID_RE` 时直接报错（模板目录用显式白名单或 `--template` 开关豁免）；README 第五步的命令改成传绝对路径。

### 主-2 「全局替换场景标识」这一步不足以把骨架包的身份换干净

README 第 10 节第一步第 3 条只说替换场景标识。照做之后，`scene.json` 的 `taxonomy` 三级仍是：

```
key : example / minimal / skeleton
name: 示例场景 / 最小子类 / 骨架产品
```

`product.name` 仍是「最小骨架示例产品（本文件不对应任何真实产品）」。`validate.py` 不检查 `taxonomy` 三级 key 是否等于场景标识的三段，也不检查 `product` 是否还是骨架文案，全部放行。

前端 `[源] data/loadScene.ts:440-462` 的 `adaptScene()` 用 `taxonomy` 三级的 `name` 拼 `SceneMeta.scene / subclass / productType` 与 `packName`，`packName` 显示在全局状态位。第三个包会带着「最小子类 · 骨架产品」上线。

修法两条。第一步的文字改成列出必改清单：场景标识、`taxonomy` 三级的 `key` 与 `name`、`product` 三字段。`validate.py` 增加一项跨文件检查，把 `taxonomy` 三级的 `key` 与场景标识的三段逐段比对。

### 主-3 十一个字段是 schema 必填，README 一个字没写

逐条核对 12 份 schema 的 `required` 与 README 全文，下列字段在 README 里出现 0 次：

| 字段 | 出现在哪几份 schema 的 required |
|---|---|
| `demo_profile` | control-parameters、datasets、safety-interlocks、test-requirements |
| `usage_class` | documents 的 `documents[]`、experience 的 `experiences[]` |
| `source_roots`、`notes` | workflows |
| `schema_note` | experience |
| `purpose_derived`、`metadata_name`、`tags`、`gzip` | workflows 的 `workflows[]` |

另有两个只出现一次、没有任何结构说明：`group_tiers`（必填于五份文件，README 第 6.2 节仅一句「骨架形状三层，层数不变」）、`criterion_expression_note`（必填于 test-requirements，README 仅在第 6.2 节的可继承清单里点了个名）。

`demo_profile` 尤其要紧。它不是装饰字段，是演示模式的驱动数据：`[源] shared/tiers.ts:157-172` 的 `demoList()` / `demoFilter()` 按它过滤参数、判据、联锁、时序四类条目，顶栏的「演示 / 全量」开关（`[源] app/TopBar.tsx:173`）就是它的入口。README 第 3.1 节列的包元字段只有五个，没有它；第 6 节「换包时哪些必换、哪些可继承」也没有它。开发不知道它是什么、该点名哪几条，只能照抄骨架包的示例条目 id。

修法：README 第 3.1 节的包元字段表补齐这十一个字段与各自的语义；`demo_profile` 单独给一小节，说明它点名的是条目 id 且换包必换；第 6.1 节「必换：内容层」把 `demo_profile` 的四类列表加进去。

### 主-4 四条红线，机读契约只落实了两条

README 第 5.2 节把四条红线写成了这套契约的可信度出口。实际落地情况：

| 红线 | 机读落实 | 变异验证 |
|---|---|---|
| 一 · `_placeholder` 只许 `true` | 已落实，`common.schema.json` 的 `placeholderFlag` 用 `const: true` | 改 `false` 被拦住 |
| 二 · `_status` 只许重写不许删 | 已落实，要求非空字符串 | 写成空串被拦住 |
| 三 · 合成数据不得进合规报告 | **未落实** | 把全部时序改 `synthetic: true` 而不写 `all_synthetic` / `why_synthetic`，放行 |
| 四 · 「未采集」不等于「不通过」 | **未落实** | `evaluable` 改 `false` 且删掉 `not_evaluable_reason`，放行 |

第 3.2 节那条「`_source.file` 一律绝对路径，不得写相对路径或只写文件名」同样只写进了 `common.schema.json` 里 `sourceRef.file` 的 `description`，没写进 `pattern`。变异测试里把 `file` 改成相对路径，放行。

修法三条，都是一行改动：`sourceRef.file` 加 `"pattern": "^/"`；`datasets.schema.json` 加条件约束，所有条目 `synthetic` 为真时要求顶层出现 `all_synthetic` 与 `why_synthetic`；`test-requirements.schema.json` 的 `requirements[]` 用 `if/then` 表达「`evaluable` 为 `false` 则 `not_evaluable_reason` 必填」——这条 README 第 3.3 节说「schema 管不住」，其实 draft 2020-12 的 `if/then` 完全管得住，说法需要更正。

### 主-5 流程标签的格式约束只贴了三处，漏了三处

`common.schema.json` 已经定义了 `flowLabel`（`"pattern": "^F[1-6] "`），但只被 `used_in_flows`、`adjustable_in_flows`、`requirements[].flows` 三处引用。变异测试里把这三处改成 `"F9 不存在的流程"`，全部拦住；下列三处改成同样的值，全部放行：

- `report-template.json` 的 `spec_sections[].from_flow`（schema 里声明成裸 `{"type":"string"}`）
- 各文件顶层的 `belongs_to_flow`（同样是裸字符串）
- `experience.json` 的 `experiences[].tags.flow`

另有 `scene.json` 的 `flows`，schema 只约束了单条的 `id` 形如 `^F[1-6]$`，没有 `minItems: 6` 也没有唯一性约束。把六条流程删到只剩两条，放行。而 README 第 6.2 节把「`flows` 六条 F1~F6 固定」列为可继承的结构层，意思是这六条不该动。

修法：三处漏贴的改成 `"$ref": "common.schema.json#/$defs/flowLabel"`；`scene.json` 的 `flows` 加 `"minItems": 6, "maxItems": 6, "uniqueItems": true`。

### 主-6 副驾按钮的红线降级规则没进 schema

README 第 8.2 节称之为「这套设计的核心约束」：触碰红线的按钮 `touches_redline` 为 `true`、`redline_action` 写明是哪一个、`degraded_to` 固定 `prepare_and_wait`。

变异测试：把一枚按钮改成 `touches_redline: true`、`redline_action: "start"`、`degraded_to: null`，放行。三个字段各自的取值域都合法，它们之间的联动关系没有任何约束。

这条的后果不是渲染问题，是安全设计被静默绕过：`[源] copilot/actions.ts:70` 的 `requiresConfirm: d.type === 'execute' || d.touches_redline` 仍会要确认，但「降级成备好等人点」这一层的表达在数据里已经丢了。

修法：`common.schema.json` 的 `button` 加 `if/then`——`touches_redline` 为 `true` 时，`redline_action` 不得为 `null` 且 `degraded_to` 必须是 `prepare_and_wait`。

### 主-7 跨文件引用全面不校验，README 只认领了其中一半

README 第 11 节第 1 条认领了四处未校验的引用：`covers_requirements`、`tags.parameters`、`maps_to`、`assets/` 文件存在性。实测确实都不拦。但同类问题还有五处，第 11 节没认领：

| 变异 | 结果 |
|---|---|
| `group_tiers` 的 `members` / `items` 指向不存在的条目 id | 放行 |
| `demo_profile` 点名不存在的参数 key | 放行 |
| `experiences[].evidence_level` 不在本文件 `evidence_levels` 内 | 放行 |
| `documents[].conversion_status` 不在本文件 `conversion_status_legend` 内 | 放行 |
| `attributes[].group` 不在本文件 `groups` 清单内 | 放行 |

后三项尤其不该漏——README 第 5.3 节明说这三个字段「必须是本文件某某 legend 的键」，这是同文件内的引用，不需要跨文件检查器，一个循环就能查。`group_tiers` 成员悬挂会直接让左栏分组渲染不出对应条目，`demo_profile` 悬挂会让演示模式静默退回全量（`tiers.ts:172` 的 `out.length ? out : items` 兜底），两者都不报错、不留痕。

修法：`validate.py` 增加 X4「同文件内键引用一致性」，覆盖上述五项；README 第 11 节第 1 条补齐认领范围。

### 主-8 `icon_draft` 是一条契约发布时就自认不该有的必填

`common.schema.json` 的 `button.required` 含 `icon_draft`。前端 `[源] copilot/actions.ts:25` 把它声明成可选（`icon_draft?: string`），全工程只有两处提到它，都是注释，没有任何读取。README 第 3.3 节自己写：「按口径落在必填里了，实际它只是草案追溯字段，前端不读。新建包若懒得填，把 schema 里这一项从 `required` 移出即可。」

契约不该把「自己知道错、请使用者自行改掉」的条目发布出去。这是「schema 拒绝但前端能跑」这一类错配里最清楚的一个标本。同类还有 `source_roots`、`schema_note`、`purpose_derived`、`metadata_name`、`criterion_expression_note`，全工程零引用，却都是必填。

修法：`icon_draft` 从 `required` 移出。其余五个若确定保留，README 要给出保留理由（比如留给构建脚本对账），不能只靠「两包共有」这条机械口径。

### 主-9 兜底脚本对一半实物包不存在

README 有三处把 `selfcheck.py` 当作 schema 缺口的兜底：

- 第 79 行：「各包 `_build/selfcheck.py` 只检前十份。」
- 第 157 行：「schema 管不住这条条件依赖，各包 `_build/selfcheck.py` 的 C3 检查会管。」
- 第 403 行：「C10 那类语言陷阱与 C9 那类文档对账，JSON Schema 原理上就表达不了，只能留在 `selfcheck.py`。」

第 405 行自己写明：「**包二目前没有自己的 `selfcheck.py`。**」两处「各包」的措辞与事实冲突。实质后果是第 9.4 节那条唯一失败项的成因——包二没有 C5 检查——同样适用于 C3、C7、C8、C10，玻璃升降器包在这五项上完全没有过检。

修法：把「各包」改成「包一」，并在第 3.3 节点名「这条兜底目前只对包一生效」。更好的做法是按主-4 把 C3 这类能用 `if/then` 表达的检查搬进 schema，减少对每包一份脚本的依赖。

### 6.3 跨文件引用未校验对开发的风险评估

按后果分三档。

**会让界面少东西、但不报错的（最危险）。** `group_tiers` 成员悬挂会让左栏该分组渲染不出条目；`demo_profile` 点名失效会让演示模式静默退回全量。两者都不抛错、不留痕，评审现场看到的是「这个包内容少」，排查要翻到前端归一化层。第三个包最可能踩的就是这两条——它们是「照抄骨架包结构、换掉内容数组」这个动作的必然产物。

**会让判定失真的。** 判据变量指向不存在的参数 key、`criterion` 引用未声明变量、FAULT 位掩码对不上，都会让判据求值出错或恒假。包一靠 `selfcheck.py` 的 C4、C5 兜着，包二与第三个包没有这层兜底。

**只影响展示的。** 资产路径不存在、顶层计数字段对不上实际条数、`maps_to` 指向不存在的文件。这类肉眼可见，翻一遍页面就能发现。

结论：README 第 11 节把跨文件引用列为「没覆盖的」是诚实的，但风险等级估低了。建议在交付第三个包之前先补上 X4 同文件内键引用检查——这一项不需要跨文件检查器，改动量小，能挡住最危险的那一档。
