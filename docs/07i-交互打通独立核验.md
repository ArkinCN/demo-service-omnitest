### 重启后凭据失效

实测：先向桥签发一张新票 `ct_iueQcVvC3Y88SdK4Be9vZUBQ`（`state=pending`、`executed=false`），此时台账 25 条；执行 `/home/zzz/lab/spike-device-mcp/run-bridge.sh` 重启（新 pid 1348101），重启后：

- 台账条数 **0**；
- `GET /confirmations/ct_iueQcVvC3Y88SdK4Be9vZUBQ` 回 **HTTP 404**；
- 带该旧票直接核销 `start`，回 `{"status":"confirmation_invalid","executed":false,"reason":"confirm_token 不存在或已被清理"}`。

结论：凭据确为纯内存，重启即全部失效，符合声称。

附带观察（非核验项，但影响后续复跑）：重启后桥的 `status` 由声称走查时的 `mode: live`、`hostname: SK-20251218QPBB` 变成 `mode: unknown`、`hostname: null`，连续探两次未自行恢复。到台架的 SSH 连接没有随桥重启自动重建。这不是本轮改动引入的问题，但会让下一次复跑走到回放态而非真连台架态，做演示前需要先确认这一项。

## 十、发现的问题（按严重级）

### 严重：构建产物明文内嵌设备桥 token，持有它即可绕过整条红线

**P1.** `npm run build` 产出的 `/home/zzz/agent-test-web/dist/assets/index-Q1rwh1Bc.js` 中，可直接搜到设备桥的共享鉴权 token 明文（与 `/home/zzz/lab/spike-device-mcp/.env` 里的 `BRIDGE_TOKEN` 同值）。这是 Vite 的 `VITE_` 前缀变量必然被打进浏览器包的结果，`.env.example` 文件头自己也写了「只有 `VITE_` 前缀的变量会进浏览器包，所以这里不能放任何私钥本体」——而 `VITE_BRIDGE_TOKEN` 恰恰放的就是私钥本体。

危害不止于泄漏一个字符串。桥的人工批准接口 `POST /confirmations/{token}/approve` 的全部鉴权就是这一个 token（`bridge.py` 的 `auth()` 只比对 `x-bridge-token` 头）。任何拿到该 token 的人，可以自己调工具签发凭据、自己调 approve 批准、再带票执行，全程不需要任何人点任何按钮。`README.md` 里「模型能调到的 13 个工具里没有任何一个能把凭据从 pending 推到 approved，这是闸口成立的根据」这句只对 MCP 工具面成立，对持有 token 的 HTTP 调用方不成立。

当前尚未造成实际泄漏：该工程不是 git 仓库（根目录无 `.git`，`git rev-parse` 报 not a repository），`dist/` 也没有被发布到任何地方。但《部署、联调与演示标准作业程序 v1.0》的流程里包含构建与 preview，一旦把 dist 交给客户或放到共享位置，等同于把台架控制权一并交出去。

建议：把批准接口的鉴权与页面读接口的鉴权拆开，批准接口改用只在服务端持有的第二份凭据（或改为桥侧本地确认、页面只做展示）；在那之前，交付任何构建产物前先确认 `.env` 中 `VITE_BRIDGE_TOKEN` 为空，并在 SOP 里把这一条写成放行门。

### 中：代码里存在一条可自动批准桥凭据的旁路（当前不可达）

**P2.** `/home/zzz/agent-test-web/src/features/agent-chat/AgentChat.tsx` 第 203–220 行，人工确认闸门 `requestConfirm` 有一个 `autoConfirm` 分支：该开关为真时直接 `resolve(true)`，并把决策记为「(演示自动放行)」，不等任何人点击。而 `/home/zzz/agent-test-web/src/features/agent-chat/api.ts` 第 414–432 行的 `confirmAt()` 在拿到 `ok === true` 且存在 `confirm_token` 时，会调 `approveConfirmation(token, CONFIRM_ACTOR, …)` 去批准桥上的凭据。两者串起来就是一条「无人点击即批准桥凭据」的路径。

当前**不可达**：`autoConfirm` 是 props，默认 `false`，两个调用点 `src/features/copilot/index.tsx:86` 与 `src/features/knowledge/KnowledgeModule.tsx:365` 都没有传它。且该文件本轮未被改动（与快照 diff 相同），风险是本轮之前就存在的。

但两点使它值得现在处理：

1. `api.ts` 第 374 行 `CONFIRM_ACTOR = '张工'` 是写死的常量，`useAppStore.ts` 第 77 行 `OPERATOR = '张工'` 同样写死。所以自动放行批出来的凭据，在桥台账里的 `approved_by` 也是「张工」，与真人批准的记录**完全无法区分**。台账的留痕因此不能作为「确有人批准」的证据。
2. `CHANGELOG-wire-20260920.md` 第一节声称「批准函数 `approveConfirmation()` 只有一个合法调用点：store 的 `approveRedline()`」。这与事实不符：`src/features/agent-chat/api.ts:427` 是第二个调用点。该文第 2.2 节自己又描述了这个调用点（「人点确认后先批准桥的凭据再发回执」），前后自相矛盾。

建议：删掉 `autoConfirm` 分支，或至少让它在存在 `confirm_token` 时强制失效；把 `approved_by` 改成带放行方式标记（人工点击 / 自动放行）的字符串，别让两者同名。

### 中：副驾的三枚红线按钮无法经界面启用，红线在该路径上无法做运行时核验

**P3.** 流程 4 的「写回草稿」「经验草稿」与流程 5 的「导出待点」三枚按钮恒为置灰，置灰理由分别是缺候选选中、缺 `/session/transcript_summary`、缺本轮产物包（其中「轮次产物存储尚未实现」是按钮自己写的）。核验人按提示在流程 4 勾选候选后，「写回草稿」仍未转为可用，说明它读的上下文指针与界面勾选不是同一处。

后果：「副驾不得自动执行」这条红线在副驾路径上目前只能靠读代码确认，没有任何运行时证据，客户演示时也无法把这条红线演示出来。

建议：把这三枚按钮的 `context_requires` 指针与实际 store 字段对齐，至少让「写回草稿」在勾选候选后可用，好让红线的「备好等人点」这一段能被实际演示与回归测试覆盖。

### 低：桥探测请求重复放大，离线时产生持续 console error

**P4.** `src/features/remote/bridge.ts` 的 `useBridgeDevice()` 是按组件实例各自建连的：`ToolRail` 的 `BridgeRail`、`DeviceMcpNode`、`flowActions.ts` 的 `useRedlineGate()` 与 `useFlowActions()` 各调一次，每个实例都自己 `pull()` 一次并各起一个 5 秒定时器，互相之间不共享缓存。实测 `/run` 页静置 20 秒：桥在线 24 次请求（设计口径约 4 次，放大 6 倍）；桥离线 48 次请求并伴随 48 条 `net::ERR_CONNECTION_REFUSED` console error（离线时每次状态轮询失败会再回落去拉一次 `/devices`，于是翻倍）。

这不影响功能，六页在离线态照常渲染。但它使「桥离线时无 console error」这条声称不成立，也让浏览器控制台在离线演示时被刷屏，掩盖真实报错。

建议：把 `useBridgeDevice` 收敛成一个模块级单例订阅，所有组件共享同一份状态与同一个定时器；离线态加退避，并把连接失败的日志降级成一条汇总提示。

### 低：文档计数与自身表格不符

**P5.** 两处：其一，`CHANGELOG-wire-20260920.md` 第二节引导句「新建 5 个文件，改动 11 个」与其下两张表（6 行 / 12 行）及实测 diff（6 / 12）不符；其二，该文第五节写「门禁 lint 21 warning」，而逐字执行 `npm run lint` 得到 43 warning，差额来自未被排除的备份目录。

建议：把引导句数字改对；在 `.oxlintrc.json`（`/home/zzz/agent-test-web/.oxlintrc.json`）里把 `.bak-src-*` 加进忽略，使文档里的 warning 计数与命令输出对得上。

### 低：`.gitignore` 当前不产生保护作用

**P6.** `/home/zzz/agent-test-web/.gitignore` 末尾写了 `.env`，但该目录不是 git 仓库（`git rev-parse --is-inside-work-tree` 报 fatal: not a repository）。该行目前是一句无效声明。真正含 token 的 `/home/zzz/agent-test-web/.env` 靠的只是「没人 `git init`」。将来一旦把这份工程纳入版本管理，`dist/` 也需要一并确认被忽略（当前 `.gitignore` 里有 `dist`，这点是对的）。

## 十二、总评

第四轮声称的功能性内容基本属实且可复现：门禁三条全过，12 步走查逐条复现且凭据为现场新签发，设备桥的三段式闸口经四项反向测试确认真实有效（闸门未满点不动、取消不进运行态、伪造票被桥 404 拒绝、桥重启凭据全灭），报告页判定计数与流程 3 一致且修复确属本轮所改，声称的删除与移动全部属实。

不能签的是「红线已经闭合」这个整体结论。三条理由：构建产物里内嵌的桥 token 使任何持有者都能自签自批绕过人工闸口（P1）；代码里留着一条自动批准桥凭据的旁路，且它批出来的留痕与真人批准无法区分（P2）；副驾侧的三枚红线按钮在界面上无法启用，该路径的红线只有静态证据（P3）。P1 建议在交付任何构建产物之前先处理。
