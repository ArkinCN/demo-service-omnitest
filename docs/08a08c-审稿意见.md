### 阻-4 ｜ 08c 第 69-82、239 行 ｜ 演示前检查单的第一项数据检查永远全绿，查不出任何缺文件

第 1.1 节步骤 5 与第二节检查项 D1 共用同一段循环，判据都是"十一行全部是 `200`"。

**先澄清一处本可能误判的地方**：第 70-71 行的循环变量列表实数 11 项（`scene`、`control-parameters`、`test-requirements`、`safety-interlocks`、`datasets`、`experience`、`documents`、`product-attributes`、`report-template`、`workflows`、`copilot-actions`），与"十一行"自洽，没有漏文件。我照原样跑了这段循环，散热风扇包与玻璃升降器包各输出 11 行、全部 `200`（见第六节）。

**真正的问题是判据本身失效。** Vite 开发服务器对 `public/` 下不存在的路径走单页应用回退，吐一份 `index.html` 并返回 200。我构造了两个反例实测：

```
/scenes/motor.cooling-fan.fortior-fu6832/NOT-A-REAL-FILE.json -> 200 <!doctype html>
/scenes/no-such-scene/scene.json                              -> 200 <!doctype html>
```

即只要开发服务器起着，这 11 行永远全 200，哪怕 `public/scenes/` 整个目录被删空。第 82 行写"任何一行不是 200，说明 `public/scenes/` 缺文件"——这个反向推断成立，但正向的绿灯毫无信息量。

同一份文档的检查项 D2 用的是 `curl -s ... | head -c 200`，判据写「返回 JSON，不是 404 页面」——D2 的做法是对的，D1 却只看状态码。两项检查紧挨着，方法却一严一松。

**为什么是阻断**：D1 是演示前 30 分钟检查单里唯一一项验证数据完整性的检查，它给出的是假绿灯。真缺文件时页面会显示"场景包未加载"（第 318 行的故障表正是为此写的），而检查单已经放行，演示者带着"数据组四项全过"的信心上场。

**改法**：判据从状态码改成内容判定。最省事的一版是把循环里的 `-o /dev/null -w '%{http_code}'` 换成取首字符，要求是 `{`；更稳的一版是 `curl -s <url> | python3 -c "import json,sys;json.load(sys.stdin)"` 判退出码。另把第 239 行 D1 的标题"散热风扇场景包**十个** JSON 齐全"改成"十一份"，与同行判据和第 82 行统一。
