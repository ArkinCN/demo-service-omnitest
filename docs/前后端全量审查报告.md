## 一、为什么要做全量审查

此前的工作方式是「用户在界面上发现问题 → 反馈 → 逐个排查修复」。这种方式有两个致命缺陷：

1. **找不完全**：同一类问题在不同地方复发，修一处漏三处（例如枚举值不匹配，前后出现过 `evidence.kind`、`artifact_kind` 两次）。
2. **有些问题在界面上根本看不出来**：本次审查发现的最大问题（`artifact_kind` 前后端七值只有两个对得上）在界面上**完全无异常**——因为调用处把异常吞了。

因此改为：以交接书为基准，**程序化比对**代替肉眼审查。

## 四、必须修的问题（逐条）

### 🔴 B-1 · `artifact_kind` 前后端七值只有两个对得上（最严重）

**证据**

后端 `c/backend/app/models/run.py:37-45`：
```python
ARTIFACT_SCHEMAS = {
    "config-snapshot", "requirement-baseline", "run-artifact", "verdict-table",
    "gap-list", "param-change", "report-instance",
}
```

前端 `c/web/src/features/flow-run/api.ts:53-60`（修复前）：
```ts
export type ArtifactKind =
  | 'config-snapshot' | 'precheck' | 'timeline' | 'measurements'
  | 'verdict-table' | 'tuning-record' | 'report-draft'
```

**七值里只有 `config-snapshot` 与 `verdict-table` 对得上。**

**判定依据**：主文档 656-661 行明列
> `artifact_kind` 取七值（一律用流程标识，不用序号）：
> `config-snapshot requirement-baseline run-artifact verdict-table gap-list param-change report-instance`

**后果链**（这才是它危险的地方）：

1. 前端 `persistRun()` 落 5 份产物，其中 3 份（`measurements`/`timeline`/`report-draft`）后端不认 → PUT 被 **409 拒掉**；
2. 而 `panel.tsx:721` 的 `catch {}` **把异常吞了**；
3. → 界面完全正常、控制台无输出，**但一轮都没存下来**；
4. → 「刷新后仍能找回轮次」这项验收长期挂着，却一直查不到原因。

**修复**

| 文件 | 改动 |
|---|---|
| `flow-run/api.ts` | `ArtifactKind` 七值改为与后端一致；`persistRun` 落的五份改名（config-snapshot / run-artifact / verdict-table / gap-list / report-instance），并新增 `gap-list`（未达标项清单） |
| `flow-run/panel.tsx` | 落盘失败不再静默：`console.error` + 新增 `persistError` 状态，写进判定卡 tooltip |
| `flow-run/api.ts` | 状态机推进失败也留 `console.warn` |

**验证**：`audit_enum_contract.py` 五组差集 **10 → 0**；`verify_run_persist.py` 端到端 **5 份写入 + 读回 5 份全过**。

### 🔴 E-1 · 9 个路由未挂鉴权

**证据**：`audit_auth_coverage.py` 报出（解析跨行签名）

| 模块 | 函数 | 风险 |
|---|---|---|
| `kb_entries.py` | `create_entry` / `get_entry` / `update_entry` / `list_versions` / `delete_entry` | **写操作裸奔**：任何人可增删改知识条目 |
| `kb.py` | `kb_search` / `create_ref` | 读 + 登记引用关系 |
| `evaluate.py` | `evaluate` | 判据求值 |
| `agent_stream.py` | `agent_confirm` | ⚠️ **阶段 5 会变成"批准危险动作"的入口** |

**为什么必须修**：`AUTH_DISABLED=false` 时（阶段 2 验收第 4 条「另一无权限用户读不到」要求切 false），这些接口全部裸奔。

**为什么修了不会破坏单机模式**：`get_current_user` 在 `AUTH_DISABLED=true` 时回退本地管理员（见 `app/api/deps.py:63`），所以加上它**只在切 false 后生效**。

**修复**：四个模块共 9 个路由补 `_: User = Depends(get_current_user)`。
知识条目是共享的、不按人隔离，故只取「已登录」一层，参数命名 `_` 明示它是门禁而非数据。

**验证**：`audit_auth_coverage.py` **9 → 0**；重启后端后 `/api/kb/search`、`/api/evaluate`、`verify_run_persist.py` 均正常。

### 🟡 C-1 · 台架工控机连接信息硬编码

**证据** `c/web/src/features/remote/device.ts`（修复前）：

## 八、维护指引（接管者必读）

**改任何协议字段前，先跑这四个脚本**：

```bash
cd c/backend
python scripts/audit_api_contract.py     # 端点缺口
python scripts/audit_enum_contract.py    # 枚举双向差集（改枚举值必跑）
python scripts/audit_code_quality.py     # 吞异常 / 硬编码 / 遗留
python scripts/audit_auth_coverage.py    # 新增路由后必跑
```

**三条纪律**：

1. **改枚举取值前，先确认下游只认哪几个值。** `evidence.kind`、`artifact_kind` 都栽在这上面——"更准确"的上游值反而让数据一条都显示不出来。
2. **禁止 `catch {}` / `except: pass` 处理会失败的业务动作。** 落盘、落库、状态推进这类，失败必须留痕，否则"看似成功其实失败"的问题无法定位。
3. **新增路由必须挂鉴权。** 跑 `audit_auth_coverage.py` 确认。

## 九、本次审查的最大教训

> **「界面正常」不等于「功能正常」。**
>
> 本次发现的最严重问题是 `artifact_kind` 前后端不一致，导致轮次**一份都没存下来**。而界面上判定卡照常显示、控制台干干净净——因为调用处把异常吞了。
>
> 这类问题的唯一解药是：**程序化契约比对 + 端到端验证 + 禁止静默吞异常**。三样缺一，问题就会一直藏着。
