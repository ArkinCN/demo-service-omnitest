### 1.1 判定口径

五态，互斥且穷尽。v3.0 写的是四态，但 1.2 表里实际用了十一种混合标签，计数因此对不上；v3.1 把混合标签归并成第五态「部分完成」，每一条只落一态。

| 判定 | 含义 | 开发要做什么 |
| --- | --- | --- |
| 原型已实现 | 代码在仓库里跑得通，行为与文档一致 | 不重做，只在改动时保持不破 |
| 假数据或脚本回放 | 界面与数据结构在，底下是写死的回放、桩实现或离线产物 | 换成真接口、真采集、真服务，结构不动 |

| 完全未做 | 一行代码没有 | 从零写 |
| 因第三轮已作废 | v2.0 的这项任务随结构改版失去对象 | 不做，改做替代项 |

>
> 第三步，写三轴分类的增删改查接口。**这一步的结构以第三轮的三轴为准，不要建成一棵树。** 三个轴是归属、来源、用途：归属三级，场景、子类、产品类型，不设第四级；来源两类，文档与经验；用途三类，产品说明书、测试需求、工艺。权威描述在 `[源] 06-第三轮改版/06a-知识分类体系与资产归类.md`，逐条落位结果在 `[源] knowledge/usage-placement.md`。前端的三轴筛选已经写好在 `[源] knowledge/data.ts`，请读它的取数口径，**服务端返回的形状要让前端那层只改取数来源、不改筛选逻辑**。

### 7.2 红线闸口的机制不许改

**难点在于工具面是给模型用的。** 如果申请与批准都做成 MCP 工具，模型调完申请再调批准就自己把自己放行了，闸口等于没有。验证工程的解法是三段式，**批准接口只挂在桥的 HTTP 面上，不做成 MCP 工具**：

1. 模型调动作工具不带凭据，工具拒绝执行，返回一张待批准凭据与一句给人看的提示。
2. 界面弹确认条把提示与参数摆给人看，人点确认后带操作人标识调批准接口。
3. 模型带着这张凭据与**同一组参数**重调同一个工具，才会执行。

凭据四道约束：单次使用、180 秒过期、绑定工具名、绑定参数指纹。为启动批的票不能用于急停，批准时是一个值、执行时改成另一个值一律拒。

**生产化时这四道约束与三段式结构一条都不许放松。** 取证在 `[源] spike-device-mcp/evidence` 下第 08 至 16 号 JSON，九份文件对应九种情形，逐一跑过。九种按结果分两组：六种拒绝——无凭据启动、未批准凭据启动、凭据重放、无凭据写参数、参数被篡改、无凭据急停；三种放行与留痕——人工批准、批准后执行、确认审计轨迹。

## 十二、六条红线与硬约束

**这一节的每一条都是硬约束，不是建议。** 分五组，来源逐条标注。

### 12.1 六个动作只能人点

| 组 | 动作 | 出处 |

四条配套约束：

安全确认闸门三项同时成立才能点启动——联锁全满足、预检通过、现场安全总闸已开。现场安全总闸必须人当场点，点了本轮有效，跑完自动复位。

急停任何时候可点，不受闸门约束；点了先发停机指令，再把当时全部状态存下来。软件急停只是补充，落地时应另有一条物理急停回路，不能拿软件急停当唯一手段。

安全联锁在数据结构上必须与普通参数分开，能不能点启动这一判断只查联锁不查普通参数。

设备侧的放行只有一条路：服务端发回一次性凭据，界面弹确认条把提示与参数摆给人看，人点确认并带操作人标识调放行接口。**批准接口只挂桥的 HTTP 面，不做成 MCP 工具**，否则模型调完申请再调批准就自己把自己放行了。

### 12.2 画布拓扑归场景包

**每条流程的默认视图与画布拓扑由场景包下发，不写死在代码里，也不塞进流程定义。** 默认视图走 `scene.json` 的 `default_view` 段，经加载层拼成场景包对象，页面走三级回落：人点过的、场景包下发的、代码兜底。

### 12.3 助手按钮的红线降级

按钮的产出只允许答复、草稿、填表三种，三者都不触发六条红线动作中的任何一个。**任何按钮的实现里出现调用这六个动作的接口，即为违规。**

涉及红线的按钮只做到把人工按钮由灰转为可点为止，动作本身不执行。界面上要如实回显入参与结果，入参写明只把人工按钮转为可点、不执行动作本身，结果写明等待人工确认、未执行。

按钮分讲解、准备、执行三类，一轮没跑完时只禁用执行类，讲解与准备类保持可点。
