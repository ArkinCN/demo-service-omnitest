# 客户代码怎样复用 v4.2

## 结论和当前进度

**客户已有代码可以作为开发起点，尤其是 API、助手会话、报告生成和设备工具。** 新网页的测试业务仍要补，但不需要把这些底层能力重新写一遍。

目前已经完成源码定位、入口核查和下面的迁移安排。**尚未把客户后端迁入当前 Gitee 仓库，尚未编译验证本清单中的客户工具，也没有完成新前端联调。** “源码里有实现”与“已在新系统可用”是两种状态。

以下路径相对于内部交付的客户“平台代码-脱敏版”。它包含 `api/`、`app/`、`debug-agent/` 等目录，和 Gitee 中的 `agent-test-system` 是两份工程。负责人须提供获授权的工作副本、版本、工具和配置说明。

## 一、作为新后端底座迁入的部分

### 1. API、用户与数据库

入口：`api/app/main.py`。认证见 `app/api/v1/auth.py`、`app/api/deps.py`；用户见 `app/models/user.py` 及对应服务；数据库和现有迁移见 `app/db/session.py`。

保留原服务组织、用户 ID 和权限依赖，在其中新增测试任务、配置快照和需求基线。原服务启动还会初始化定时器及种子数据，首次启动用独立数据库和文件目录，不能连客户原生产环境。

原数据库有 MySQL/SQLite 相关处理，先验证选定分支。此前建议 PostgreSQL 只是方案建议，未完成兼容验证；这次先不迁数据库类型，以免同时改业务与存储。

**先验什么：**原登录/权限正常；新增任务重启后仍可读；第二用户不能读第一用户的任务。客户单机安装里的免登录配置不能作为多人权限验收。

### 2. 真正的助手后端与聊天存储

入口：`api/app/api/v1/agent_chat.py`、`app/services/agent_chat_service.py`、`app/services/agent_stream_manager.py`。聊天保存另见 `app/api/v1/chats.py`、`app/services/chat_service.py`、`app/models/chat.py`。

已有模型调用、工具循环、流式响应、取消和断线后重订阅。新系统优先复用这条链路，只补当前任务上下文、工具权限和新页面协议适配。客户事件如 content_delta 与当前页面的 message_delta 等不能直接混用，需逐项映射。

客户流缓存依赖单 worker 内存。浏览器断线重连可复用已有机制；服务进程重启、多 worker、设备动作恢复仍需新做。不要再同时启动另一套 DSH 模型循环造成重复调用。已有 DSH 插件按工具需要评估接入，不能把两套会话引擎都设为主链路。

**先验什么：**新页面发送当前任务问题，复用客户服务得到真实回答；换任务后上下文改变；取消、断流和重启分别得到正确状态。

### 3. 模型网关与额度

入口：`api/app/services/gateway_service.py`、`app/models/gateway.py`；额度见 `app/models/credits.py`、`app/services/credits_service.py`、`app/api/v1/credits.py`。

保留模型选择、调用前余额检查、实际 usage 计费、流水关联和周期刷新。沿用原用户及共享额度池，不从前端自报消耗。额度单位、初始规则和价格行为如需改，另列产品变更，不在移植时悄悄变化。

**先验什么：**一次调用对应一次结算；重复事件不重复扣费；并发调用、取消及失败时，余额和流水与原规则一致。实际价格与模型配置由负责人提供。

## 二、保留执行代码，加一层网页可调用接口

### 4. 报告：优先调用已有库

入口：`writeFile_rust/src/processor.rs`；现成接法见 `app/src-tauri/src/integrated_test_system/report/commands.rs` 的 `generate_report`。

**这里已经支持变量填充。** 桌面入口把工作表名、行列、数值和图片等映射交给 `write_file_rust::processor::process`，返回写入数量、警告与成功状态。此前检查到 CLI 的 `variable_data=None`，只是命令行入口没有传变量；不能据此要求重写整个填表能力。

新做一个受控适配器，接收业务系统的模板/文件 ID，调用原库，返回产物 ID、摘要和下载入口。开发接口不开放任意服务器路径。

**先验什么：**用测试模板、一张图片、一个数值和一份 CSV 生成文件，在表格软件打开核对；有警告时逐条判断，不能只看退出码。这个无硬件样例可以和 API 迁入验证并行做。

### 5. 编译、烧录和参数辨识

编译入口：`debug-agent/src/compilation/compile_with_download.rs`，已有 compile_only、download_only、compile_and_download_only。辨识入口：`debug-agent/src/commands/param_identification.rs`，已有 start/stop 和结果结构。

保留既有工具调用和日志处理，在可访问 Windows 工具、串口和驱动的主机上加 HTTP/MCP 适配。网页提交任务和受权文件引用；服务端负责路径校验、超时、参数范围、设备占用和审计。模型及设备凭据不从浏览器传入工具。

**先验什么：**先做请求转换和隔离工程的 compile_only，确认日志及产物摘要；再按现场批准流程验证烧录、读回和辨识。全局取消标志需改造成按任务/设备隔离，不能直接支持多台并行。

### 6. 仪器控制与读状态

可从 `app/src-tauri/src/integrated_test_system/power_supply/commands.rs` 追到已有连接、设定和遥测；`debug-agent/src/transport/`、`oscilloscope/` 及独立 RIGOL 工程提供其他设备入口。

优先复用现有协议实现，让现有设备桥调用受控适配器。先验证识别设备、读设定和读测量，随后才验证带批准的输出开关、写入和启停。HTTP 请求被接收不代表物理动作完成，要等设备回执或读回。

**先验什么：**一条真实只读状态返回包含设备身份、单位、时间和 live/mock 标识；拔线或工具失败不会变成成功值。

## 三、复用逻辑，但需要抽离场景或桌面依赖

### 7. 工作流执行器

入口：`app/src/features/integrated-test-system/workflow/engine/WorkflowExecutor.ts`。已有执行、暂停、停止、循环、嵌套和运行配置快照，但它位于桌面前端，依赖 store、toast、Tauri API 和节点注册表。

保留执行顺序、状态和取消逻辑，抽离界面调用；设备动作由服务端适配器执行。不能把 TypeScript 文件原封不动搬到 Python 后端就认为可运行，也不能只搬画布而丢掉执行器。

**先验什么：**用一个已知工作流和无硬件节点执行器，核对事件顺序、循环、失败和取消；显式装载适用的节点注册表，未知节点拒绝执行。

### 8. 具体产品的调优流程

入口：`debug-agent/src/applications/vacuum/startup_adjust/executor.rs`；调度入口可追 `app/src-tauri/src/agent_debug/commands.rs` 的 `start_debug_workflow`。

已有初测、调优、验证的函数链，可以参考和复用适用模块。但吸尘器、吹风机、散热风扇的参数与条件不相同，不能把一种产品的流程直接当通用算法。源码中仍有固定的尝试次数返回，需要改为实际计数。

**先验什么：**列清适用场景、参数映射和停止条件；用可控模拟结果验证失败后怎样选下一候选、怎样取消，以及预算耗尽后怎样转人工。再由现场人员确认实机参数。

## 四、当前项目确实还要新增的部分

原代码覆盖的是其原有业务。新系统仍需增加测试任务和多场景版本、不可变配置与判据、运行产物关联、任务权限、设备租约、幂等批准、未知动作对账，以及新前端与这些服务的接口。

这部分按 [后端开工顺序](README.md) 推进。复用模块也需要回归，不把“源码存在”写成“已经能部署”。配置中已发现疑似硬编码凭据，迁移前要清理；原安装脚本、账户和网络地址不能原样带到新部署。
