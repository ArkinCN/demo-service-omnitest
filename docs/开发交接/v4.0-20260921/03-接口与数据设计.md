# 接口与数据设计 v4.0

本文是待开发契约。除明确列出的现有入口，表里的接口需要同事实现，不能直接拿来调用。字段命名、路径和数据库选型属于本版建议；业务约束是必须满足的要求。

## 1. 服务怎样分工

浏览器只调用业务 API。业务 API 保存任务、校验权限、运行判定、管理报告，并调用助手服务。助手服务负责模型和检索，工具执行仍经过业务 API。设备桥部署在能连接测试台的机器上，只接受业务服务的请求。客户的 Rust 工具通过适配器接入，不让模型拼接任意 shell 命令。

建议首版采用同一个业务服务、一个任务工作进程、关系数据库和文件目录；设备桥独立部署。助手可作为 Node 工作进程接 DSH，也可以接项目选定的模型 SDK，但必须实现本文的事件协议。不要为了演示先拆一组无人维护的微服务。

旧 P2 已指定优先复用客户 FastAPI 的用户、登录依赖和额度模块，本版保留这条实现起点。迁移时先保留额度内部单位 `1_000_000` 和内测每日额度 `500`，用原模块行为做回归；是否调整额度属于产品决策，不能在换框架时顺手改掉。PostgreSQL 是本版存储建议，采用前要核实原模型和迁移兼容性。

## 2. 所有新接口共同遵守的规则

- 用户身份从登录会话取得，不能相信请求里的 `operator`、角色或权限。只读者能查看；操作员能建任务和申请动作；批准者能批准获授权的动作；管理员负责配置。是否允许申请人与批准人相同，由项目负责人决定，默认高风险动作分离。
- POST 创建和设备动作带 `Idempotency-Key`。服务端按用户、任务、接口和键存请求摘要；相同请求返回同一结果，不再执行；同键不同内容返回 409。记录不能仅放进进程内存。
- 修改已有资源带 `expected_version`。版本不符返回 409，并返回当前版本；冻结后的配置和基线只允许派生新版本。删除被运行引用的对象返回 409。
- 通用错误形如 `{"error":{"code":"VERSION_CONFLICT","message":"配置已被其他人修改","retryable":false},"request_id":"…"}`。400 输入错误；401 未登录；403 无权；404 不存在；409 状态或版本冲突；422 业务条件未满足；429 限流；503 依赖不可用。不能用 HTTP 200 包一个失败结果后让前端继续成功流程。
- 列表使用 `cursor/limit`；文件使用不透明 ID，服务端校验所属任务、类型、大小和摘要。客户端不能传服务器任意路径。日志记录 request_id、用户和对象 ID，删除 PIN、密钥及模型凭据。

## 3. 业务 API 清单

以下以 `/api/v1` 为前缀。输出至少包含资源 ID、版本和状态。开发时交付 OpenAPI 文件及可执行请求示例，不能只保留此表。

### 3.1 账号、场景、配置与要求

| 方法与路径 | 输入 | 输出与处理 | 主要拒绝条件 |
| --- | --- | --- | --- |
| POST /sessions；DELETE /sessions/current；GET /me | 登录方式由部署方配置 | 登录、退出、当前用户与权限 | 错误身份、过期会话 |
| GET /credits；GET /credits/transactions | 当前用户、分页游标 | 余额、额度规则、用量明细 | 不暴露他人额度；扣减在服务端幂等结算，不接受客户端自行报账 |

| POST /tasks/{id}/firmware-backups | 固件资源 ID、读取方式 | 文件 ID、SHA-256、设备标识、读取日志 | 无读取能力时不得伪造备份 |
| POST /tasks/{id}/identifications；GET /identifications/{id} | kind=hardware/motor、设备及配置 ID、方法、批准请求引用 | 作业状态、原始证据、带单位的辨识结果草稿 | 不支持的场景、缺联锁、需激励却未批准 |
| POST /configuration-templates；GET /configuration-templates | 可复用字段、场景、版本 | 参数模板；不包含样机身份或现场批准 | 不得把临时现场确认存成默认通过 |

## 4. 已有 SSE 怎样兼容

现有前端 `web/src/features/agent-chat/api.ts` 使用 `POST /api/agent/stream`，输入为 `text/model/permission/auto_run/session_id`；解析 `message_delta`、`tool_call`、`tool_result`、`verdict`、`evidence`、`done` 六类事件。目前不能据此认定业务后端已交付。

旧解析器实际按 data JSON 内的 `type` 分发，消息字段用 `messageId`、`callId` 等 camelCase，不能只发送 SSE 的 event 名。确认入口为 `POST /api/agent/confirm`，请求体 `call_id/approved/actor/confirm_token`；actor 必须由服务端会话核验。当前解析器在 EOF 时会补发 done complete，需要改为只有明确完成事件或查询到已完成状态才显示成功。

旧协议文字示例：`data: {"type":"message_delta","messageId":"m-1","delta":"正在核对配置"}`，事件后接空行；终结为 `data: {"type":"done","reason":"complete"}`。解析还需测试 CRLF、跨网络块的 JSON、多行 data 和重复终结事件，不能只在完整 LF 字符串上通过。

第一步可以在业务服务实现这个兼容入口，再逐步切换上面的会话接口。新的任务上下文、事件 ID 和缺数据状态需要同时更新前后端，并注明协议版本。现有 `verdict.pass` 是布尔值，不能把“待人工”“无数据”都塞成 false 后显示为实测失败。

建议新事件格式如下；这是 v2 建议，现有解析器不能直接使用：

```text
id: 17
event: tool_result
data: {"protocol_version":2,"turn_id":"turn-1","call_id":"call-2","status":"ok","result_ref":"result-3","summary":"读取到本轮三次起动记录"}

id: 18
event: verdict
data: {"protocol_version":2,"criterion_id":"start-success","state":"missing","reason":"缺少规定的有效试验次数","evidence_refs":[]}

id: 19
event: done
data: {"protocol_version":2,"reason":"complete"}
```

事件须持久化、严格递增并去重。流断开不代表工具失败；恢复时查询 turn 和 action 的实际状态。模型超时返回错误与可重试说明，禁止静默切回回放并显示“真实助手”。工具开始前先保存执行记录，结束后保存原始结果引用和摘要。

## 5. 保存哪些数据

关系数据库建议使用 PostgreSQL，具体版本在部署锁文件确定。以下不是已经存在的表：

| 数据组 | 最少内容 | 保存规则 |
| --- | --- | --- |
| users、sessions、roles | 用户、会话摘要、角色和作用域 | 密码/令牌不得明文；登录可复用既有受维护服务 |
| tasks、scene_versions | 负责人、阶段、场景版本、version | 页面刷新和服务重启可恢复 |
| snapshots、baselines | 完整 JSON、schema 版本、摘要、创建与冻结信息 | 冻结后不可原地改写 |
| runs、run_events、artifacts | 状态、开始/结束时间、实际参数、事件、文件摘要 | 原始数据与派生结果分别存；历史回放单独标记 |
| assistant_sessions、turns、messages、drafts | 模型配置引用、上下文版本、事件和草稿 | 保存必要来源；敏感上下文按权限读取 |
| action_requests、actions、device_leases | 请求摘要、批准记录、一次性凭据摘要、回执、占用租约 | 动作状态与幂等键持久化；原始 PIN 不落库 |
| verdicts、gaps、parameter_changes | 判据引用、计算输入、缺口、版本链与 diff | 不覆盖上轮结果；保留判定算法版本 |
| knowledge_items、chunks、import_jobs | 分类、文件、版本、页码、索引版本、软删除时间 | 索引重建不能丢原始资料及来源 |
| reports、exports、archives、audit_events | 模板版本、字段来源、复核、文件和操作者 | 报告引用固定版本；归档之后派生修订版 |

七份既有产物 JSON Schema 从原设计规格的第 15 节提取，见 `contracts/`。它们描述归档产物，不足以直接承担实时作业状态。例如运行中尚无 ended_at，不能强行伪造结束时间来满足归档 Schema。实现运行表及完成时的产物转换器，并在转换边界校验。任何扩展先提高 schema 版本，不悄悄改旧枚举含义。

## 6. 状态与异常恢复

运行建议：draft → queued → prechecking → awaiting_approval → running → collecting → evaluating → completed。任一阶段可以进入 failed；执行中收到停止请求进入 stop_requested，设备确认后为 stopped。无法确定设备是否执行时为 unknown，锁住后续写入，先人工核对设备和回执。

批准与执行分开：requested → approved/rejected/expired；approved → executing → succeeded/failed/unknown。批准的完整参数摘要、配置版本、目标设备和有效期必须一致。批准后改一个参数也要重新申请。

数据库事务先记录动作和幂等键，再发命令；网络超时不能证明没有执行。恢复进程先查询设备或读取实际参数，以 action_id 对账。支持取消的工具才能被真正取消，不支持的要显示“已请求取消，等待工具结束”。

文件写入临时路径，计算摘要后原子移动，再登记可下载状态；失败时清理临时文件并保留错误记录。备份恢复同时覆盖数据库、产物文件及索引版本，不能只恢复数据库而让报告链接全部失效。

## 7. 接口交付必须附带的例子

后端至少提交一条完整无设备示例，以及以下失败示例：同键重复请求、同键不同参数、版本过期、无权限、缺数据、批准超时、PIN 锁定、工具返回业务失败、执行后丢失回执、文件缺失。示例包含请求、响应和数据库/文件变化；接口文档必须由同版本代码导出并纳入回归。
