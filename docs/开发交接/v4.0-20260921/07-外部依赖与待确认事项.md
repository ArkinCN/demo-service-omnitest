# 外部依赖与待确认事项 v4.0

本版已经把可据现有材料写清的开发工作列出。下列信息需要项目负责人、客户或现场人员补充，不能由开发者凭感觉填值。它们不妨碍先做无设备开发，但会阻塞对应的现场或正式发布步骤。

## 1. 需要确认的业务与现场条件

| 编号 | 谁提供 | 需要给出什么 | 缺失时影响 | 开发可先做什么 |
| --- | --- | --- | --- | --- |
| D01 | 客户测试负责人 | 每个场景的测试项、阈值、单位、样本数、判定公式、标准版本及适用条件 | 不能宣布产品合格，不能把示例值当正式值 | 完成可配置判据和模拟边界测试 |
| D02 | 现场安全/设备负责人 | 硬件急停、软件急停、断网/断电策略，哪些动作需批准，最长可接受停止时间 | 当前急停立即执行需求与 PIN 机制冲突，真实动作发布受阻 | 先实现接口和模拟故障，保留独立急停要求 |
| D03 | 设备与固件负责人 | DUT/板卡/固件版本，接线、量程、通道、联锁阈值、可写参数白名单及限值 | 无法安全执行或烧录 | 用模拟设备和受限参数模型开发 |
| D04 | 产品负责人 | R-14 数量口径、目标屏幕/缩放；R-11 真人浏览器结果 | 不能签首屏与滚动体验验收 | 同时提供分区和全页计数，记录截图和尺寸 |
| D05 | 项目负责人 | 申请/批准角色是否可相同，报告复核角色、归档保留期限 | 正式权限策略和报告签收未定 | 按最小权限及高风险分离的建议实现配置 |

## 2. 需要交给开发者的材料

| 编号 | 提供者 | 材料及版本要求 | 对应任务 |
| --- | --- | --- | --- |
| M01 | 项目负责人 | 客户脱敏代码的内部访问方式、准确提交或文件摘要、允许使用范围 | T11、T14、T22、T24 |
| M02 | 客户/固件人员 | 编译器、烧录器、驱动、许可证、头文件、链接配置、可复现固件工程 | T11、T22、T23 |
| M03 | 设备人员 | 通信协议、设备手册、现有工具版本和可运行样例，真实设备与预约时段 | T12～T19 |
| M04 | 客户测试人员 | 正式报告模板、字段字典、样例合格报告、图片/CSV/变量填充规则 | T24、T25 |
| M05 | 项目/运维人员 | 模型服务账号、网络可达性、部署主机/系统/架构、域名、备份和登录方案 | T02、T07、T30、T31 |

这些资料通过获授权的内部渠道交付。当前包不包含客户完整源码、固件工程、正式标准和凭据。开发者应在依赖清单写“已收到哪个版本”，不能仅写“本机有”。

## 3. 必须进一步核实的技术项

| 编号 | 核实内容 | 明确结果应是什么 |
| --- | --- | --- |
| V01 | 客户 dc-skills 正文及每个 action 的 skill_ref | 找到实际文件，记录输入、步骤、工具和权限；名字存在不等于可直接调用 |
| V02 | DSH 锁定版本的 Node 集成接口及重连/取消能力 | 最小程序、真实事件样例、许可证和依赖；不要照旧文档中的伪代码接 Python API |
| V03 | 客户吸尘器调优逻辑对当前电机/汽车场景的适用性 | 可复用通用部分与需重写的场景假设，核实源码中的固定次数等字段 |
| V04 | 客户工作流节点、前端解析与真实执行器的交集 | 每种节点能否执行、输入输出、异常和不支持原因；能画出来不代表能运行 |
| V05 | 报告工具变量填充能力 | 解决 CLI 当前 variable_data 未传入的问题，提供字段、图表和缺项样例 |

## 4. 如何关掉这些缺口

旧 04-v3.1 第 13 节还留下三项具体口径，必须承接：通道映射存在两套冲突（并入 D03，以客户接线说明为准）；候选排序以当前证据级优先实现作为起点，业务负责人确认后再改；知识条目有 15 条 usage_review 待人工分类，其中跨来源边界条目不可自动拍板。T06 应输出这 15 条的逐项分类确认表并保留旧标签。

旧版 1360/1120 宽度断点仍作为页面验收输入。若本轮画布结构不适合旧抽屉/单列方案，由前端提交两尺寸下的实际布局给产品负责人确认，不能只测大屏后删除此要求。

每项填写负责人、收到日期、版本/摘要、确认结论和关联验收证据。确认结果回写配置、接口、任务及验收矩阵；只在聊天里说一句“不用管”不作为正式配置。涉及客户限值和安全策略的变更保留确认记录。

交付文件可以先转给同事开工；D01～D05、M01～M05、V01～V05 的状态必须随开发更新。没有证据的项保留待确认，不用猜测补成“已完成”。
