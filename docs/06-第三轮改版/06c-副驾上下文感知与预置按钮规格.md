## 一、上下文包

### 1.1 它解决什么问题

现在的原型每次发消息只带一句话 prompt，副驾要靠这句话猜自己在哪个页面。上下文包（context envelope）把"当前在哪、当前看的是什么、刚才发生了什么"结构化地随请求发过去，副驾不再猜。

发送时机两处：人手打字发消息时，以及点预置按钮时。两处用同一个结构，按钮只是多带一个 `action` 字段说明点的是哪个按钮。

### 1.2 结构分七段

按"谁在用、在哪一步、三个区各是什么状态、刚跑出什么、查到什么、能做到哪"切分，七段各回答一个问题，互不重叠。

| 段 | 回答的问题 | 主要字段 |
| --- | --- | --- |
| `session` | 谁在用、这是哪一轮会话 | 会话标识、操作人、本轮已发生的对话摘要 |
| `product` | 测的是什么产品 | 场景包标识、三级分类路径与显示名 |
| `flow` | 在六个流程的哪一步 | 流程标识、当前步骤、各流程的确认状态 |
| `zoneB` | 左栏表单现在是什么样 | 分组结构、当前值、未填项、占位项、选中项、联锁、判据、控制参数 |
| `zoneC` | 右上画布与设备现在是什么样 | 选中节点、工作流节点表、设备清单与状态、台架占用 |
| `lastRun` | 最近一次运行跑出了什么 | 轮次标识、判定结果、未达标项、产物包索引、预检结果 |
| `kb` | 知识库这次查到了什么 | 检索命中条目、转化状态汇总、经验库汇总 |
| `policy` | 副驾这次能做到哪一步 | 权限档位、自动执行开关、红线动作清单 |

`policy` 与前七段并列，共八段；前七段是描述现状，`policy` 是约束边界，性质不同，单独列。

## 二、按钮体系

### 2.1 三类按钮的判定规则

分类维度只有一个：**这一下点下去，改变了什么**。

| 类型 | 改变了什么 | 确认闸门 | 举例 |
| --- | --- | --- | --- |
| 解释类 | 什么都不改，只产出文字与依据 | 不弹 | 把当前页面讲给我听 |
| 准备类 | 只改前端暂存态：草稿、清单、候选、待确认队列 | 不弹 | 帮我填好、帮我查缺项 |

## 四、换场景不变性

### 4.1 三层切分

| 层 | 内容 | 换场景时 |
| --- | --- | --- |
| 结构层 | 上下文包的八段结构、按钮的字段定义、三类按钮的语义、红线降级规则 | 不变 |
| 编排层 | 每个流程有哪几枚按钮、按钮 id、图标、类型 | 不变 |
| 内容层 | 预置 prompt 里的业务名词、`skill_ref` 指向的规程、`operation` 的工具名 | 换 |

落地方式：把 `06c-copilot-actions.draft.json` 复制进场景包目录成为 `copilot-actions.json`，与现有的 `control-parameters.json`、`test-requirements.json` 等并列。前端按 `sceneId` 读，读不到就退回本文件这份默认骨架。

| `touches_redline` | true，写回参数 | true，写回参数（同） |

**一句话验证：** 两个场景对比下来，`id`、`label`、`type`、`touches_redline`、`degraded_to`、`context_requires` 全部相同，变的只有 `source`、`skill_ref`、`prompt`、`operation` 四个字段。这正是"结构相同只换内容"。

**升降器场景的数据诚实性约束不放松。** 该场景包的时序数据是合成的、判据数值来自征求意见稿，所以它的解释类与准备类按钮的 prompt 必须额外带一句"引用数值时标明来源状态"，执行类按钮在该场景下第一版不开放——没有真设备可连。

## 五、交互细节

### 5.1 位置与折叠

按钮条放在对话框输入区上方一行，横向排列，与输入框同宽。一行最多显示 5 枚，第 6 枚起收进末尾的"更多"下拉。可见的 5 枚按流程在 JSON 里的书写顺序取前五，顺序即优先级。

窄屏时可见数量按容器宽度递减，最少保留 2 枚加"更多"。按钮只显示图标加文字，不用纯图标——纯图标在不熟悉的功能上认不出来。

### 5.2 随流程切换

切流程时按钮条整条替换，不做动画堆叠。切换后上一流程的按钮不保留，因为按钮的 `context_requires` 是按流程写的，跨流程点必然缺字段。

**置灰规则**：`context_requires` 里有字段取不到时按钮置灰，悬停提示缺什么、去哪补。举例，流程 ④ 的"比对历史"在第一轮还没跑过时是灰的，提示"还没有可比的历史轮次"。

### 5.3 点击后的三段

| 段 | 做什么 |
| --- | --- |
| 回显 | 在气泡里先把 `echo` 那句话显示出来，讲清将要做什么、会不会改东西 |
| 确认 | 执行类按钮在这里弹确认卡片，走组件既有的 `requestConfirm` 闸门；解释类与准备类不弹，直接进下一段 |
| 执行 | 按 `operation` 逐条发工具调用，结果按既有的 `tool_call` 与 `tool_result` 协议回填卡片 |

回显不是可选项。用户点按钮时并不知道这枚按钮背后预置了什么 prompt，先回显再执行，等于把预置内容摊开给人看。

### 5.4 执行类的确认闸门

复用现成机制，不新造。副驾组件工程 `[源] agent-chat/README.md` 第二节已定义：带 `mutating: true` 的工具调用先进待确认态，卡片描边转暗红，给"确认执行 / 取消"两个按钮；适配器通过 `SendRequest.requestConfirm` 拿闸门，**未注入闸门时按不放行处理**。现有实现在 `[源] copilot/adapter.ts` 已经照此写好。

输入区的"开启自动执行"开关只覆盖只读类工具，不覆盖改动类动作。执行类按钮的确认卡片不受该开关影响。

### 5.5 副驾按钮与 C 区工具条的分工

客户截图上画布右侧有一列竖排工具按钮，分三组：波形采集、环境控制、MCU 调试。这一列与副驾按钮条是两套东西，分工按"谁在操作"切：

| | C 区竖排工具条 | 副驾按钮条 |
| --- | --- | --- |
| 谁在操作 | 人直接操作设备与画布 | 人让副驾去做一件事 |
| 一次做几步 | 一步 | 一串，可能含检索、推理、多次工具调用 |
| 有没有文字产出 | 没有，改的是画布与设备状态 | 有，气泡里给说明与依据 |

两者可以指向同一个底层能力。举例，C 区的"采波形"按钮直接抓一次波形，副驾的"预检自检"里也会抓波形，但后者抓完还要判读并给结论。
