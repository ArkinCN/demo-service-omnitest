## 零、先读这五句

1. **业务逻辑不在代码里，在文档里。** 六个流程各自要算什么、人在哪里介入、哪些动作不许自动做，全写在 `docs/20260919-通用Agent测试系统v2.0/02-业务逻辑说明-六个流程.md`。动手前通读，尤其是第七节「开发者最容易搞错的六件事」。

2. **原型已经有壳和四个真组件，缺的是服务端与真业务。** 前端应用壳、设计系统、六条流程路由、四个功能组件已经能跑并出截图；判据求值、知识库检索、智能体会话、设备控制全部是回放或桩。现状逐条见第一节三态表。

3. **前后端接口以《设计规格》第 15 节为准。** 七份产物的 JSON Schema 草案写在那一节，字段名一律 snake_case，与场景包已落盘的 JSON 对齐。不要另起一套字段名。

4. **数据不要自己造，全在场景包 JSON 里。** 散热风扇场景包在 `[源] scenes/motor.cooling-fan.fortior-fu6832`，十个 JSON 加一份 README 加实测波形。包内带 `_placeholder: true` 的十二处是占位，界面必须标「待确认」，不得当真值参与计算。

5. **智能体不要另起炉灶，接已有的 DSH 骨架。** DSH 指 DeepSeek Harness，深度求索开源的 agent 运行时，npm 包名 `@deepseek-ai/dsh`，源码 `https://github.com/deepseek-ai/deepseek-harness`。本项目的插件骨架在 `c/components/dsh-plugins`，已跑通「加载技能 → 调工具 → 判定 → 安全 Hook 拦截」的端到端链路。

## 十一、顺序与并行

### 11.1 主链与支线

**主链四段，不能跳。** 服务端骨架 P2 出来之前，知识库 P3、智能体 P4、业务逻辑 P6 都没有落脚点；设备侧 P5 的真实现出来之前，业务逻辑 P6 的判据只能标未采集。

```
P2 服务端骨架 ──▶ P3 知识库 ──┐
                              ├──▶ P6 业务逻辑补全 ──▶ P8 联调与演示
P5 设备侧 ──▶ P4 智能体集成 ──┘
```

**两条支线可以全程并行。** P1 从原型到可维护工程只依赖前端自身，第一天就能开工；P7 第二场景包只依赖 P1 与 P2，但建议排在 P6 之后做，那时六条流程已是真逻辑，换包演示才有说服力。

### 11.2 三个人分工的建议排法

| 人 | 第一段 | 第二段 | 第三段 |
| --- | --- | --- | --- |
| 前端 | P1 | P6 的界面侧 | P7、P8 的前端部分 |
| 后端 | P2 | P3 | P6 的服务端侧 |
| 设备与智能体 | P5 | P4 | P8 的台架部分 |

**P4 与 P5 交叉，排给同一个人。** 智能体的三个 MCP 桩要换成设备侧的真实现，两包的契约对齐反复来回，拆给两个人会持续对不上。
